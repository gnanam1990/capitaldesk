## Limitations

- **No venue contact, and none claimed.** This module reads no account. It consumes an
  observation cut recorded by module 05, whose authenticated boundary remains BLOCKED for want
  of a `VENUE_READ` credential — so in a live deployment there is currently no way to obtain a
  COMPLETE cut, and bootstrap would refuse. That is the correct behaviour, and it means the
  end-to-end path is blocked upstream rather than here.
- **Cost basis before the opening is unknown, by construction.** A baseline taken from a
  balance snapshot records what is held, not what it cost. `cost_basis_known` is false and
  there is no path that sets it true, so no complete P&L or tax claim can be made from it.
- **Conservation is proven for the transitions that exist.** Reserve and release are module
  04's and are covered by its own suite; fills, commissions and quarantine arrive with module 14. T-012's full sweep is not complete until then.
- **An intermittent full-suite failure, characterised rather than smoothed over.** Across nine
  full integration runs on the development machine, two failed. Both were the _first_ run
  immediately after a full compile, and in each case the failing suites passed in isolation
  seconds later. The failures were in suites this module does not touch, and they differed
  between the two occurrences, so they do not point at a specific test.

  What was ruled out: connection exhaustion. Peak backends observed during a full run were 17
  against a `max_connections` of 100. What was not established: the actual cause. The
  correlation is with a busy machine rather than with any code path, and CPU contention against
  the harness's 20-second statement timeout is the plausible explanation — but plausible is not
  proven, so it is recorded as an open observation. Continuous integration runs the suite on a
  dedicated runner and is the independent evidence to watch.
