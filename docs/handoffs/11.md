## Public contracts

- `ApprovalRepository.decide` records one exact `APPROVED` or `DECLINED` owner decision per
  plan. It binds plan digest, account epoch, policy and ledger revisions, FIFO allocation,
  intent revisions, algorithm version, fee policy, per-strategy debit/commission caps,
  approval expiry, submission deadline and execution mode.
- `ApprovalRepository.revoke` atomically invalidates and releases an unmarked plan. When a
  marker already exists it records `HALT_REQUESTED_IN_FLIGHT`, halts the pool, and preserves
  the plan and reservation as unresolved liability.
- `ApprovalRepository.recordNativeConfirmation` stores an independent, immutable
  `BINANCE_AGENTIC_MCP` confirmation only when its confirmed payload digest exactly matches
  the locally approved plan digest. It is an internal service contract and is not exposed as
  a public HTTP assertion endpoint.
- `ApprovalRepository.eligibilityOn(client, input)` is the transaction-owned last-moment
  executor check. It validates plan state, exact digests, revocation, strict expiry and
  submission deadline, active mandate version, post-seal ledger revision, active strategy
  authority, exact execution mode, and native confirmation where required. Every known-plan
  decision is written to immutable `plan_dispatch_eligibility_checks` evidence.
- Owner HTTP routes:
  - `POST /v1/workspaces/:workspaceId/pools/:poolId/plans/:planId/approval`
  - `POST /v1/workspaces/:workspaceId/pools/:poolId/plans/:planId/approval/revoke`
  - `GET /v1/workspaces/:workspaceId/pools/:poolId/plans/:planId/approval`
    State-changing owner routes require a live owner session and CSRF token. The response
    exposes the displayed FIFO schedule, all strategy caps and the partial-fill FIFO consequence.

## Failure scenarios proved

- T-006: a changed plan digest cannot reuse approval; approval rows are append only.
- T-007: equality with the submission deadline expires the plan and releases unmarked holds;
  dispatch equality with the approval expiry returns and persists `APPROVAL_EXPIRED`.
- T-008/T-040: later ledger activity, mandate version change or strategy archival blocks
  dispatch eligibility.
- T-025: repeated approval and decline replay their durable decision; reuse of one key for a
  different execution mode is a body conflict.
- T-039: approved-host mode remains ineligible until a separate exact native confirmation is
  stored.
- Owner decline and unmarked revocation return the reservation and UTC budget hold in the same
  transaction. Revocation after a marker retains capital and halts the pool.
- A proposal agent cannot create an approval decision.

## Limitations and next prompt

  belong to module 12. It must call `ApprovalRepository.eligibilityOn` inside the marker
  transaction before signing or sending.
